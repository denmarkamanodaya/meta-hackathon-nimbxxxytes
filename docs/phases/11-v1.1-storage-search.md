## A2: "nimbytes" drive (NFS v3 loopback served by the app), the approved approach

- **Mount:** the Mac app runs a user-space NFS v3 server on 127.0.0.1 (crate `nfsserve`, approved
  2026-10-27; new code only). It mounts the drive at `~/nimbytes`, as the user with no root, with a
  volume name of "nimbytes". There is a mounted-drive icon on the Desktop: a Finder alias placed on
  the Desktop, plus a `.VolumeIcon.icns` served at the volume root with the nimbytes logo. If Finder
  shows connected servers on the Desktop, that works too.
- **Tree:**
  - `Library/` has every ready clip's **original**: full size, and reported space used = bytes
    actually cached, so Finder shows "Zero bytes on disk" until it is read.
  - `Shorts/` holds the renders.
  - `Projects/` holds the FCPXMLs, generated on demand.
  - `Exports/` is writable; a file written there uploads through the existing multipart flow.
- **Reads:** byte ranges come from S3 (presigned original URL, HTTP Range) into a sparse chunk cache in
  Application Support, LRU-capped (default 5 GB). The used bytes reported per file = its cached chunks.
- **Migration:** the existing `~/nimbytes` mirror folder (real copies from v1.0.1) is renamed to
  `~/nimbytes (v1.0.1 copies)` before mounting. Nothing is deleted without the owner's yes.
- **Mac window:** plays proxies from the cloud, with replay served from the same cache. There is no
  full-library proxy mirror any more (B).
- **Lifecycle:** mounts at app start (Launch at login is already in the menu) and unmounts cleanly at
  quit. If the app is not running, the folder is empty; the menu-bar status says so.
- **Spike first (≤ 3 h):**
  1. Non-root mount works.
  2. Get Info shows "Zero bytes on disk" for an uncached clip.
  3. QuickTime plays a clip read through the mount.
  4. DaVinci Resolve imports an FCPXML that points at mount paths.
  5. The Desktop icon shows.


## Context

The owner tested v1.0.1 and raised four points. Findings were measured on the owner's Mac and in the
code on 2026-10-27, read-only.

### #1 Storage: every clip is stored, so the folder grows without limit

- Today `~/nimbytes` holds **182 MB for 4 clips, about 65 s of footage**:
  - `Library/` proxies 38 MB
  - `Originals/` 94 MB (2 originals auto-cached for the FCPXML)
  - `Shorts/` 50 MB
  - `Exports/` 0.4 MB
- The proxies are heavy. `api/crates/adapters/src/media/args.rs` encodes them at H.264 veryfast CRF 23,
  1280 px, 30 fps, with no bitrate cap. Busy POV footage comes out near **8 Mbit/s**, e.g. 16.8 MB for
  17 s, about a third of the original.
- Projection per hour of footage:
  - proxies about 3.5 GB;
  - originals about 11 GB;
  - **a 10-hour library is about 35 GB of proxies on the Mac before any original.**
- Sync copies every ready clip's proxy, always (`desktop/src-tauri/src/services/sync.rs`). So the Mac
  fills up as the library grows. That is a mirror, not intelligent storage.

### #2 Search: every new search makes 2 Muse Spark round trips in a row

- Pipeline in `api/crates/core/src/usecases/search.rs`:
  - Spark **rewrite** (about 1.5–2 s);
  - BM25 (Tantivy) + PE text embedding + sqlite-vec KNN, all local, all on the server, together under
    100 ms;
  - RRF fusion;
  - Spark **rerank** with reasons (about 2–3 s).
- The index *is* local (Tantivy + sqlite-vec). Clips are not re-searched; only the query goes to Meta.
- Measured: 3.6 s locally and 4.8 s on the server for a new query; 0.04–0.06 s for a repeat (model cache).
- The cost is the waiting on the two sequential Spark calls, not tokens: about $0.002–0.003 per new search.
- The cache key is the exact query plus the known names. "Dog" and "dog " are different searches.

### #3 Sync page

The four tiles (Library, Originals, Shorts, Projects) and the Smart cache card expose internals the user
never needs. The owner wants the media to just load and the Mac's storage left alone.

### #4 "Zero bytes on disk"

- Finder's Get Info shows "Zero bytes on disk" only for **dataless files** managed by an Apple **File
  Provider** extension. That is the same mechanism as iCloud Drive's "Optimize Mac Storage" and Dropbox's
  online-only files.
- Our app writes real files today, so it can never show that.
- The tooling is there: Xcode 26.6 and macOS 26.5. The owner's Developer ID is in the Keychain.

## A: File Provider, technical outline

- **New:** `desktop/fileprovider/`, a Swift package or Xcode target producing `nimbytes File Provider.appex`.
  - It is sandboxed, with the App Group `4M2FU676CS.dev.denmarkamanodaya.nimbytes` (team-prefixed, so it
    works with Developer ID and needs no provisioning profile).
  - The Tauri build copies the appex into `nimbytes.app/Contents/PlugIns/` and signs it with the same
    identity.
- **Main app:** registers the domain with `NSFileProviderManager.add(_:)` through a tiny Swift helper,
  called from Rust (a `swift-rs` bridge or a bundled CLI helper). It writes the session cookie and server
  origin into the shared App Group container. Sign-out removes the domain and wipes the container.
- **Extension:**
  - *Enumerator:* reads `GET /api/sync/manifest` with its ETag and maps clips, shorts and projects to
    `NSFileProviderItem`. The item version comes from the manifest etag fields, and size from
    `size_bytes`.
  - *fetchContents:* `POST /api/sync/clips/{id}/original`, then a URLSession download into the provided
    temp URL.
  - *createItem in Exports:* the duplicate check, then the multipart upload. Upload logic is ported to
    Swift; it is small.
  - *Signals:* the main app calls `signalEnumerator` after each 30 s manifest poll, so new clips appear
    without the extension polling.
- **FCPXML:** Projects are generated by the main app and written into the domain, pointing at the domain
  URLs of the originals. NLEs opening them trigger on-demand downloads.
- **Kept from v1.0.1:** Rust sync engine (manifest polling, state), Keychain, menu bar, the Mac window,
  FCPXML writer. The `~/nimbytes` mirror folder becomes migration-only. On first launch of v1.1, offer to
  move it to the Trash once the domain is live.
- **Spike (go/no-go, half a day):**
  1. An unnotarized, Developer ID–signed app with an embedded appex registers a domain on this Mac.
  2. A placeholder shows "Zero bytes on disk" in Get Info.
  3. Opening it in QuickTime downloads it.
  4. DaVinci Resolve imports an FCPXML whose media are dataless and materialises them.
  If 1 fails without notarization, the fallback is an owner decision: notarize, or keep the mirror and
  ship B + D only.

## A3: smart-aware cache (owner approved 2026-10-27; owner's name for it)

Built on the A2 drive's chunk cache.

- **Eviction order** (a pure core rule, unit-tested):
  1. never: chunks of open files, and clips the owner keeps on this Mac;
  2. last: segments used in shorts and in Projects FCPXMLs;
  3. middle: chunks recently watched or matched by recent searches;
  4. first: raw footage nobody searched, used or watched.
  Ties go oldest-access first.
- **Limits:** 5 GB by default. The cache also shrinks while the Mac's free space is below 15%.
  "Free up space" on the Sync page clears everything that isn't protected.
- **Prefetch:** when a short reaches ready, or its FCPXML is written, the drive downloads only the
  byte ranges of the segments it uses (from segment start_s/end_s, mapped to byte ranges), so opening
  the timeline in an editor is instant.
- **Sync status:** `cache_bytes` (shown as "Space used on this Mac"). Protected bytes are counted in
  it too.
