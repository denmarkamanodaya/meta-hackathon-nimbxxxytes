# Investigation: why Phase 23 analysis is slow (2026-10-28)

**Asked by the owner:** "note the hiccup that the slow comes from Meta's models; provide a full investigation log to back this claim up."

**Verdict (evidence below):** the claim is **only partly true**.
1. **The main cause is our own request bug, not Meta's speed.** SAM detect calls sent the whole clip inline as base64, about 41 MB, without `store:false`. Meta's API processed each one for about 2.5 minutes, then **rejected it with HTTP 413**, and our client retried 3 times. These failed calls are **86 % of SAM detect waiting time** (105.9 of 122.8 min). Meta's error message names the fix itself.
2. **Second cause: our pipeline waits on one remote call at a time.** Sightings, evidence and pair checks all run one after another.
3. **What Meta's model latency itself costs** (successful, uncached calls; durations from our side, network included):
   - Muse Spark: ~9–10 s per video moment, ~28 s per two-image pair check.
   - SAM 3.1 video: ~60 s for ~130 frames at 1280 px; ~5.7 s per single image.
   - Voice Transcribe: ~31 s per clip.

   That is real, but per call it's reasonable. It only becomes "slow" multiplied by sequential calls and retries of rejected requests.
4. **Not the cause:** our machine. The API container's CPU was under 1 % while analysis "ran", with 2 of 7.6 GB memory used.

So the honest line for the record is: *"The slowness came from how we called Meta's models (oversized inline requests rejected after processing, and one call at a time), not from the models being slow."*

## Method
- **Source:** the ledger table `model_calls`. Every model call is logged by `MetaClient` with model, purpose, latency_ms (wall time from our side), billed frames, tokens, cost, cache_hit, status and error.
- **Window:** `at > 2026-10-28T13:30Z` (the Phase 23 run).
- **Read from a copy:** the DB was **copied** (`cp nimbytes.db*` to the scratchpad) and queried with `sqlite3` on the copy. The live file was never opened (CLAUDE.md rule 12).
- **Snapshot time:** 2026-10-28 15:02 UTC.
- **Raw data**, in `docs/investigations/2026-10-28-latency/`:
  - `model_calls.csv`: every call in the window, 852 rows.
  - `summary_by_purpose.csv`: the table below.

  - `docker_stats_*.csv`: container CPU and memory during the run.

### 2. SAM detect: failed calls dominate

| Status | Calls | Avg s | Total min |
| --- | --- | --- | --- |
| error | 44 | 144.4 | **105.9** |
| ok | 17 | 59.7 | 16.9 |

The error breakdown:
- **36 × HTTP 413**, verbatim:
  > `{"error":{"code":"payload_too_large","message":"This response could not be stored because the request is too large (~41 MB) to persist with store=true. Upload large media via the Files API and reference it by file_id instead of inlining base64 data, or retry with store=false."}}`
- **8 ×** `sam-3.1 gave up after 3 attempts: transport: error sending request for url (https://api.meta.ai/v1/responses)`: large uploads timing out or dropped.

Our cause:
- The SAM body (`api/crates/adapters/src/meta/sam.rs`, `metadata` at line ~304) sets `include_confidence` and `mask_encoding` but **not `store:false`**. All our Spark bodies send `store:false`.
- It also inlines the video as a base64 data URL. The `rrr` detect step sends the clip's 1 fps copy at 1280 px (about 130 frames on average here), so big clips produce about 41 MB requests.
- The spikes used 640 px and 60 frames (about 9 s per call, no errors).

### 5. Other things that slowed tonight (operational, not model speed)
- **Home uplink saturation:** while 2 GB of originals uploaded, the ingest proxy upload to R2 failed (clip `A1_943308_a`). The fix was 720p sample copies uploaded one at a time.
- **Three API restarts** while jobs ran: each claim counted an attempt, so clip `A1_943308_d` used up its retries at the proxy step and was re-uploaded.
- **Too many sightings before the rule fix:** about 60 per 4-min clip, so 390 evidence SAM calls. Commit `41a8c96` folds repeats within 15 s and caps at 12 per clip.

## Fixes (feed the performance pass, phase 23 doc §9d)
- **P0 (new, from this investigation):** SAM bodies send **`store:false`**, and large media goes through the **Files API (`file_id`)** instead of base64. This removes the 413s and the retries, the biggest single win.
- **P1:** detect on a 640 px 1 fps copy with fewer frames for long clips; concepts in parallel.
- **P2:** bounded parallel calls in sightings, evidence and pair checks.
- **P3:** reuse the ingest face boxes; SAM image only for plates and screens.
- **P4:** pair check with 1 frame each.
- **P6:** keep this query as `scripts/latency-report`, run on a DB copy.
- **Re-measure** after the pass with the same query and compare against `summary_by_purpose.csv`.
